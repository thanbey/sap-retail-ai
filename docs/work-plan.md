# Two-Week Prototype Work Plan: SAP Retail AI (Sentinel, PIR, Financial Reconciliation)

**Assumptions:** full time (about 7 hours a day, 10 working days), S/4HANA and AIF mocked with SAP CAP on your laptop, BTP trial plus AI Core free-tier booster plus the 30-day Generative AI Hub trial, everything in one GitHub repo.
**End state:** a working demo you can run in 15 minutes that shows Sentinel diagnosing and remediating AIF errors with approval, a PIR insights dashboard with anomaly flags and narratives, and a POS-to-FI reconciliation workbench, all on a shared Python AI service deployed to BTP.

---

## Ground rules for the two weeks

Start the Generative AI Hub trial on Day 2, not Day 1, so the 30-day clock covers the whole build plus a buffer for interviews or demos. Commit to GitHub every day with a short README update; the repo is a deliverable in its own right. Every synthetic dataset must be generated by a script in the repo, never hand-edited, so you can regenerate at any size. Keep a `DECISIONS.md` log; the reasoning behind choices is interview material.

## Repo layout (create on Day 1)

```
sap-retail-ai/
  service/            FastAPI app: connectors/, llm/, rag/, agents/, ml/, audit/
  mock-s4/            CAP project exposing S/4-shaped OData (AIF errors, articles, sites, PI docs, FI/POS)
  data/               synthetic data generators (aif_errors.py, pir.py, pos_fi.py)
  notebooks/          model training and evaluation
  ui/                 Streamlit workbench (Sentinel approvals, PIR dashboard, Recon workbench)
  deploy/             manifest.yml / mta.yaml for BTP Cloud Foundry, AI Core serving templates
  docs/               architecture.md, DECISIONS.md, demo-script.md
```

## Week 1: platform and Sentinel AI

### Day 1 (Mon): accounts, scaffold, mock S/4

Morning: create the BTP trial account, add the AI Core and AI Launchpad free-tier booster, create a HANA Cloud instance (enable the vector engine), install the cf CLI and log in. Create the GitHub repo with the layout above, a Python 3.11 virtualenv, FastAPI hello-world with `/health`, pre-commit with ruff, and a Makefile.
Afternoon: `cds init mock-s4`, define entities for `AIFMessage` (interface, namespace, version, status, errorClass, messageText, payload JSON, timestamp), `Article`, `Site`, `PhysicalInventoryDoc`, `CountResult`, `POSTransaction`, `FIDocument`. Run `cds watch` and confirm OData V4 endpoints. Write `connectors/s4.py` with a thin OData client (httpx) that reads from the mock and will later point at a real host via the BTP destination service.
Deliverable: repo skeleton, mock S/4 serving empty entities, connector test passing.

### Day 2 (Tue): Generative AI Hub, HANA vector store, LLM module

Morning: start the Generative AI Hub trial, create a deployment for one model in AI Launchpad, install `sap-ai-sdk-gen` (Generative AI Hub SDK for Python), make one successful chat completion and one embedding call from `llm/client.py`. Put credentials in `.env`, never in code. Add a fallback provider class so the same interface can hit Ollama or any OpenAI-compatible endpoint after the trial.
Afternoon: `rag/store.py` using hdbcli against HANA Cloud with a `REAL_VECTOR` column; write, embed and query a handful of test documents. Add Pydantic structured-output helper in `llm/structured.py`.
Deliverable: `make smoke` runs an LLM call, an embedding, and a vector search end to end.

### Day 3 (Wed): synthetic AIF error dataset and knowledge base

Morning: `data/aif_errors.py` generating 5,000 to 10,000 AIF messages across 8 to 10 retail interfaces (POS sales inbound, article master distribution, price/promotion, goods receipt, vendor invoice, stock transfer, store order, payment settlement). Define 12 to 15 error classes with realistic message text patterns (missing article at site, unit of measure mismatch, blocked vendor, period closed, duplicate IDoc, mapping value not found, tolerance exceeded, and so on), each with a labelled resolution type. Add 10 to 15 percent noise and free-text variation using the LLM to paraphrase so the classifier is not trivial. Load into the CAP mock.
Afternoon: write 20 to 30 short runbook documents (one per error class plus interface descriptions and a mock "close procedure") in `docs/kb/`, chunk and embed them into HANA. Model them on real AIF and Cloud ALM terminology using the public Cloud ALM demo tenant as a reference.
Deliverable: populated mock, RAG returns the right runbook for a sample error.

### Day 4 (Thu): error classifier

Morning: notebook: TF-IDF plus metadata features (interface, message type) into LightGBM or logistic regression, stratified split, precision/recall per class, confusion matrix. Target 90 percent plus macro-F1 on the synthetic set; record the numbers in `docs/`.
Afternoon: package the model in `ml/classifier.py` with `predict(message) -> (class, confidence)`. Create an AI Core serving template and deploy the model as a REST endpoint on AI Core free tier (if quota fights you, serve it inside the FastAPI app and note it in DECISIONS.md, then retry later). Add a confidence threshold in config below which cases go to the LLM path.
Deliverable: `/classify` endpoint, evaluation report committed.

### Day 5 (Fri): Sentinel agent and remediation policy

Morning: `agents/sentinel.py` using LangGraph (or Pydantic AI): nodes for fetch context (payload, article, site, similar past incidents from vector store), diagnose (LLM with RAG, structured output: root cause, confidence, proposed action, explanation), policy check, act, verify, record. Typed tools in `agents/tools.py`: `restart_message`, `reprocess_after_fix`, `correct_field`, `create_ticket`, `notify_owner`, each implemented against the CAP mock.
Afternoon: `agents/policy.py`: allow-list per error class, auto-execute only when confidence above threshold and action is low risk; everything else queued for approval. `audit/` writes every step to a HANA table. Run the agent over 200 errors and print the auto/approve/escalate split.
Deliverable: Sentinel runs end to end against the mock with audit trail; week-one demo recorded as a screen capture.

## Week 2: PIR dashboard, reconciliation, deploy, demo

### Day 6 (Mon): Sentinel approval workbench and BTP deployment

Morning: Streamlit page `ui/sentinel.py`: queue of proposed actions, diagnosis text, evidence, approve/reject/edit buttons that call the service; rejections are logged as training feedback. Add a retrain script that folds feedback into the classifier.
Afternoon: `deploy/manifest.yml`, `cf push` the FastAPI service to the BTP trial, bind HANA Cloud, confirm `/health` and `/classify` publicly (protect with an API key for now; note XSUAA as next step). Deploy the CAP mock to CF too, or keep it local and expose via a Cloud Connector-free approach (just point the service at a public mock for the demo).
Deliverable: Sentinel running on BTP with the workbench.

### Day 7 (Tue): PIR data and anomaly model

Morning: `data/pir.py`: 50 stores, 2,000 articles, 6 months of movement, monthly cycle counts with planted anomalies (miscounts, systematic shrink in a category, receiving errors at a store, timing differences). Load PI docs and count results into the mock.
Afternoon: notebook: Isolation Forest or z-score on expected-versus-counted given movement history, plus a simple variance driver attribution (rules or a small tree model). Measure recall on the planted anomalies. Package in `ml/pir.py`.
Deliverable: anomaly flags with precision/recall numbers.

### Day 8 (Wed): PIR insights dashboard

Morning: Streamlit page `ui/pir.py`: variance by site, category, article; trend; ageing of unposted differences; flagged counts table. Use plotly. If time allows, mirror the key tiles in SAP Analytics Cloud trial or SAP Build Apps free tier to show BTP-native UI.
Afternoon: LLM narrative per site ("what happened, why, what to do") generated through `llm/` with structured output; buttons to request recount or open a Sentinel investigation via typed tools.
Deliverable: PIR dashboard with narratives, deployed alongside the service.

### Day 9 (Thu): POS-to-FI reconciliation

Morning: `data/pos_fi.py`: daily POS sales by store and tender versus FI documents, with planted breaks (timing across midnight, missing postings, wrong GL mapping, duplicates, rounding/FX). `ml/matcher.py`: deterministic exact-key match, then a learned fuzzy matcher (LightGBM on amount delta, date delta, store, tender similarity) producing match confidence.
Afternoon: `agents/recon.py`: for unmatched items classify the break with RAG over the close procedure, draft the explanation and a proposed correcting entry; approval flow reuses the Sentinel policy and audit modules. Streamlit page `ui/recon.py`: matches, breaks, proposals, approve to "post" into the mock FI.
Deliverable: reconciliation workbench with auto-match rate and break explanations.

### Day 10 (Fri): hardening, docs, demo

Morning: XSUAA or API-key auth on the service, retry and logging on connectors, a `make demo` target that regenerates data, starts mock and UI, and seeds a handful of interesting cases. Write `docs/architecture.md` with a diagram (Mermaid), `docs/demo-script.md` (15-minute walkthrough), and a metrics section: classifier F1, auto-remediation rate, PIR anomaly recall, recon auto-match rate.
Afternoon: record a 10 to 15 minute demo video; do a dry run explaining how each piece maps to the job description (Python, BTP, AI Core, Generative AI Hub, agentic loop, Cloud ALM as ingestion source and ops monitor, Datasphere as the production analytical store). Tag `v0.1` in GitHub.
Deliverable: repo, video, architecture doc, demo script.

## Daily rhythm

First 30 minutes: review yesterday's commit, update `DECISIONS.md`, pick the day's deliverable. Last 30 minutes: commit, update README status table, note blockers. Do not let any single blocker (AI Core quota, HANA provisioning, CAP quirks) consume more than 90 minutes; work around it, log it, and move on.

## Risks and fallbacks

| Risk | Fallback |
|---|---|
| AI Core free tier quota or provisioning delays | Serve models inside FastAPI; keep the AI Core serving template in the repo and note it |
| Generative AI Hub trial not approved immediately | Use the fallback provider (Ollama locally or any OpenAI-compatible API) through the same `llm/` interface |
| HANA Cloud trial instance stops (trial instances pause daily) | Startup script that restarts it; pgvector or DuckDB as a local dev alternative |
| CAP learning curve | Keep the model small; CAP's built-in mock data (csv in `db/data/`) is enough |
| Scope creep in the UI | Streamlit only; SAP Build or SAC tiles are a bonus, not a requirement |
